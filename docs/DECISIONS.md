## OPEN — do not assume

- O02: Exact official district/village source file and its reuse terms. BPS/KPU are approved sources; import contract and provenance tracking are implemented.
- O03: Exact TPS scale, expected concurrent users, photos per report, retention.
- O05: Hosting budget, disaster recovery objectives, storage location, backup retention.
- O06: Whether a witness may be assigned multiple TPS (schema supports it, policy TBD).
- O07: Whether multiple Super Admin accounts will be provisioned (recommended to avoid approval deadlock).
- O08: Approved exact event/contest list for first release.

**Rule:** Open items should not trigger speculative feature development. If a milestone depends on an open item, request a decision before coding that milestone.
D30. `Peta Wilayah` is a dedicated authenticated page at `/peta-wilayah`, not a dashboard anchor. It reuses the dashboard read model and server-side event/contest/region scoping, is available to Super Admin and Coordinator, and keeps Witness access disabled because witness workflows remain TPS-focused.
D31. `Monitoring TPS` is a dedicated authenticated page at `/monitoring-tps` for Super Admin and Coordinator. It reuses the contest-aware dashboard read model and server-side assignment scope; client-side search/status filters never broaden the rows authorized by the backend.
D32. Dashboard geographic filters cascade from Kabupaten/Kota to Distrik to Kelurahan/Kampung. Each selection is sent to the server as the active region scope, so KPIs, verified vote totals, maps, progress, and TPS monitoring are recomputed together; options are restricted to the event snapshot and the signed-in user's accessible TPS hierarchy.
D33. The top-level Papua map uses a locally stored, dissolved BIG province layer to show the six Indonesian Papua provinces as one regional context. The active Province Papua keeps its nine kabupaten/kota overlay and drilldown; the other five provinces are visual context only until they are explicitly added to the application's master/event scope.
D34. The Papua map uses an interactive, locally rendered Leaflet hierarchy. Province and Papua kabupaten/kota layers are visible at overview; district boundaries appear from zoom 8 and village/urban-village boundaries from zoom 11. BIG district/village geometry is visualization-only and never creates master regions or broadens an event/result scope. Supiori keeps an explicit overview label because its island geometry is small at six-province scale, without a dedicated region-specific control.
D35. The interactive map uses the standard online OpenStreetMap raster tile service as geographic context beneath the local BIG GeoJSON overlays. OpenStreetMap attribution remains visible, no tiles are prefetched or offered for offline download, and a tile failure leaves the local administrative layers usable. Production traffic must continue to comply with the current OSM tile usage policy or migrate to a suitable hosted/self-hosted provider as usage grows.
D36. Vote entry remains TPS-only. The report picker cascades from event and contest to Pilkada pairs or Pileg electoral district/parties/candidates, then Kabupaten/Kota, district, village, and TPS. District, regency/city, and province results are automatic aggregates of Super Admin-approved TPS results; official recap documents at those levels are comparison evidence, and discrepancies must be flagged without adding or replacing source votes.

D37. Production HTTP hardening uses per-user named rate limits so one abusive or malfunctioning client cannot consume the quota of other field officers. Readiness at `/ready` checks database and cache but returns no dependency details. Production boot fails closed when debug, HTTPS, key, PostgreSQL, Redis cache/queue, or secure encrypted sessions are misconfigured.

D38. Official district, regency/city, and province recaps are immutable comparison records, not vote sources. Only Super Admin creates a version; Coordinator may inspect versions inside their assigned hierarchy and Witness has no access. Each version stores the approved-TPS snapshot, participant and total deltas, private evidence checksum, and audit entry. Later TPS approvals make an old snapshot visibly stale but never rewrite it. Recap creation and final approval use the same contest-row lock order to prevent mixed snapshots.

D39. Production TPS and recap evidence use one configurable private S3-compatible disk with server-side encryption; each database row retains its disk and object key so legacy local objects remain readable during a controlled transition. OCR reads through a storage stream into a short-lived OS temporary file and always removes it. Redis owns cache, rate limits, encrypted sessions, and queues; supervised scheduler/worker heartbeats are part of readiness. Release hooks never auto-rollback database migrations because schema rollback requires a migration-specific, backup-verified decision.

D40. Performance optimizations must preserve authorization and source-of-truth semantics. Approval rows are scope-filtered in SQL before pagination. Dashboard aggregation may be cached for at most a short configurable TTL using a key that includes user, event, contest, region scope, and accessible TPS set; Redis cache is never authoritative. Heavy district/village GeoJSON is loaded only at its visible zoom level, and global Vite prefetch is disabled so lazy chunks remain lazy. Capacity acceptance remains open until O03 targets are owner-approved and measured on production-like staging.

D41. P4 capacity profile: a province-scoped event supports up to 5,000 TPS and a regency/city-scoped event up to 600 TPS, with 500–1,000 concurrent provincial users. Every TPS report holds exactly one private original photo no larger than 10 MB. The application may generate a private compressed preview for viewing, but downloads and audit evidence always retain the original file. Low-resolution or malformed images are rejected before report storage; final human review remains responsible for vote-legibility decisions.

D42. P4 acceptance baseline: test three simultaneously active events using up to 1,000 users split 700 Witness / 280 Coordinator (200 reviewing, 80 dashboard-only) / 20 Super Admin; ramp 10 minutes, sustain 40 uploads per minute for 30 minutes, burst 80 uploads per minute for 10 minutes, and observe recovery for 10 minutes. p95 targets are 1.5 seconds login, 2 seconds dashboard and approval, and 10 seconds upload. Error rate may not exceed 1%; queue lag may not exceed 60 seconds. Integrity failures always fail the run.

D43. Owner deferred authenticator-based MFA for V1. Evidence uploads use a separate private-network ClamAV service and are scanned synchronously before object storage or database writes. Production configuration fails closed if malware scanning is disabled or has no configured host; local development may disable it explicitly. Scanner connection, timeout, non-clean result, or malware detection rejects the upload.

D44. Production CSP uses a per-response nonce for inline Ziggy bootstrap and Vite-generated tags, so script-src no longer permits `unsafe-inline`. Inline CSS remains temporarily permitted because Vue/UI style attributes require a separate compatibility audit; this exception does not extend to scripts.
